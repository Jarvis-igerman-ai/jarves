# JARVES setup and installation help

Help in the user's language, one short step at a time. Ask what they see, wait, then advance. Read the full relevant guide with workspace_read (follow next_offset); do not recite this document. The workspace injection is a bounded summary.
First inspect features_list, list_skills and get_status. Describe only tools/features actually available. FEATURES.md is the complete generated feature catalog (including disabled/unavailable features); TOOLS.md lists executable tools, settings and voices. A feature switch being ON is not proof that its service works. Re-check status after the user's action. A user saying 'done' is not a live test.
I can explain, inspect status with my tools, and open the dashboard using open_dashboard when requested. I have no general installer, shell or browser-control tool. Commands below are for the user to run; never claim I ran them. Do not invent commands or download links. Never install, download, activate paid/high-risk features, publish apps, or change security settings just because the user asked for guidance. Keys/passwords/codes belong only in the relevant private input or provider sign-in page, never chat, speech, memory or workspace docs. The user handles login, permission and administrator prompts. After two failed attempts, stop and report the exact non-secret error and next support step.
Topics below: JARVES install; AI/key/ChatGPT; Google Calendar/Gmail; music/Pear; voice/wake; camera; dashboard/phone; Skills; updates/backups; offline recovery. For unsupported software, say there is no built-in installer; do not pretend a suggested command is an implemented tool.

## Feature prerequisites through the CLI
The user's jarvis features on ID checks prerequisites before claiming activation, even for an already-on feature. Supported source-camera/wake dependencies install from the existing frozen lock and preserve extras; face recognition downloads only the official size/hash-pinned SFace model. Environment/model setup requires Core stopped (jarvis stop, then repeat); installed builds missing bundled dependencies need repair/update, not a developer environment. Failed, cancelled or non-installable prerequisites return a failure/pending reason and preserve the previous switch. The normal installed app bundles voice, camera and tray dependencies. This is a bounded CLI installer, not a general shell tool I can invoke. Other requirements such as missing hardware, Pear not running, Google scope consent, OS approval and paid access remain explicit user steps. A successful dependency check does not prove real capture/recognition/playback.

## JARVES installation
Use only a maintainer-provided JARVES release link. Do not invent a public download URL. Windows builds bundle Python, the face and dependencies; ordinary users do not need uv, Git, Godot or a developer environment. The owner must supply a release before it can be downloaded. The user runs the installer and approves any system prompts. Then run JARVES and its connection setup. For source developers only: core/README.md documents uv sync; never make that the normal app-user path. Pi installation/performance and physical hardware remain unverified.

## AI connection, API key and ChatGPT
Ask which connection the user wants and explain its cost source: ChatGPT plan, API key, or combined. Use the existing jarvis setup wizard (language, connection and key, name, wake phrase, voice, every add-on on/off; re-run it any time to change a choice; the dashboard Setup & add-ons page shows the same). For an API key, the user runs jarvis key and pastes into its hidden local input, never tells me the key. For ChatGPT, jarvis chatgpt login opens provider sign-in; the user handles login/consent. Paid cloud voice requires the separate API route; never promise plan-paid cloud voice or silently switch to billable API use. Ask the user to set budget limits. Use jarvis doctor and provider status to diagnose; saved settings alone do not prove live success.

## Google Calendar and Gmail
For an app build with the app-owned OAuth client: dashboard Connections, Connect Google, choose account, review permissions, approve. No gcloud, Cloud project or JSON download for app users. If the release lacks its app client, tell the maintainer it needs configuration; do not ask ordinary users to become Cloud developers. Check current connection with google_connect_help or status tools, then ask permission before a content-reading test. Calendar editing additionally needs jarvis google login --calendar-write and the user's Google consent, then jarvis features on calendar_write; granting the scope alone does not enable editing. Developer/private-client fallback only: jarvis google start guides project/API setup using installed gcloud and the remaining Console steps. Missing CLI: use Google's official Cloud CLI installation page; sign in with gcloud auth login and select the real project ID, not the display name. The user creates their own Desktop client and downloads it only in this developer path. Registration, brand/privacy-policy domain and Google verification for public users are maintainer tasks; never claim publishing is done. Testing-mode clients can expire weekly; reconnect signs in again, not seven setup pages. Gmail sending stays off unless explicitly enabled; drafts must be read back and confirmed.

## Contacts, relationships and sharing events
For natural-language typed requests with JARVES stopped, use jarvis execute "add a calendar event tomorrow at 10 called Dentist". This creates a short-lived text session with existing AI/budget, local memory, Google tools, feature gates and terminal confirmations, then exits. jarvis execute --interactive "add an event tomorrow" keeps follow-up context; Enter at the reply prompt finishes. Missing details must be asked, never guessed; single-request users can rerun with the full clarified request. This does not start Core, Godot, audio, camera capture, scheduler or background tasks. Runtime-only requests require starting their normal services explicitly. This is broader than the older jarvis ask tool set. Account permissions and feature prerequisites remain required. No live account action is authorized by setup guidance alone.

When the user explicitly says "remember my wife's email is ...", use contact_remember with their relationship/name and exact email. This is ordinary local memory: contact_lookup finds it across restarts, and recall/forget/dashboard memory controls can inspect/delete it. Never save an example address as a real contact. Existing unstructured memories can be found with recall. Conflicting details require clarification and forgetting the old entry before replacement; do not silently overwrite or infer a relationship.

Google Contacts is a separate opt-in read-only lookup, not an automatic address-book import. The maintainer must enable People API in the app's Google Cloud project. The user runs jarvis google login --contacts and approves Contacts consent, then jarvis features on google_contacts and restarts Core to load the tool. Google consent preserves earlier grants only when Google actually returns them. Use google_contacts_search by known name/email prefix; return candidates, ask which person/address is intended, and wait for the user's answer before action. No automatic spouse inference, contact edits or saving remote data. CLI: jarvis contacts search "Dana"; jarvis contacts remember "my wife" --email spouse@example.com; jarvis contacts lookup "my wife"; jarvis contacts forget MEMORY_ID. The address above is only an example.

Calendar guest invitations use calendar_create_event guests or calendar_find_events then calendar_share_event. Existing guests are preserved; recurring-event scope must be chosen. Read-back includes recipients and requires approval. This shares the event, not access to the entire calendar. Google sends invitation notifications; never claim the recipient received or accepted them. Use only a real returned htmlLink if the user also wants a link emailed; missing link is a blocker, never invent one. Existing gmail_create_draft then gmail_send_draft requires separate read-back approval. Reading third-party Contacts/event content blocks model actions until a genuine next user turn; ask for the intended selection rather than bypassing that guard.

CLI paths: jarvis calendar create --help; jarvis calendar find --help; jarvis calendar share --help; jarvis mail draft --help. Draft without --send creates only a draft. Adding --send offers confirmation and sending in the same CLI session. A new CLI process cannot send a draft from the previous process under the current fresh-draft safety policy. Feature flags, sign-in and scopes still apply. No contact reading, invitation or email is authorized just by asking for setup help.

## YouTube Music / Pear Desktop
Check music status first. A missing Pear installation needs the official Pear Desktop release, not Spotify Premium, cookies or streaming extraction. jarvis music open opens an existing installation and reports its official download link if absent. The user installs and signs into YouTube inside Pear. Then jarvis music pair and the user clicks Allow in Pear. Verify with jarvis music status; pairing does not prove actual playback. A requested playback test must confirm the song is playing. Do not claim I can auto-install or silently restart Pear.

## Microphone, speakers and wake word
Use jarvis doctor first; jarvis doctor --sound plays a test sound only when the user wants it. Check mute, selected device, availability and the user's OS permissions. Do not disable a privacy switch for them. For wake calibration, jarvis wake test; --apply saves the threshold only with approval. This records microphone input, so explain and obtain agreement first. In an installed Windows build dependencies are bundled; missing source-development dependencies belong in core/README.md. Live cloud voice needs a configured API route and spending permission. Listening must be ready before a speech test; silence and speaker echo are not recognition success.

## Camera and face recognition
Camera and recognition are opt-in; use features_list for prerequisites and approval requirements, not an invented camera installer. Open dashboard Features if requested. The user chooses whether to enable them and approves on screen; leave privacy switches in their chosen state. Face enrollment requires that person's permission. Missing hardware/model/download/network permissions are explicit blockers. Never claim a connected camera or working recognition from a switch or mock test alone.

## Dashboard and phone access
Use open_dashboard when requested, or the user can run jarvis dashboard. Existing dashboard pages expose memory, workspace docs, settings, Skills, costs, diagnostics and feature switches. For a phone, home-LAN access is opt-in and requires pairing/login plus the dashboard_lan feature. Do not expose router ports, invent a public URL, or claim HTTPS/remote-internet access is configured. If the network is down, use the PC console and local diagnostics.

## Skills and all features
Use features_list and list_skills, then read FEATURES.md / TOOLS.md for what exists and what is off or missing. Use list_settings for actual editable choices. Explain one feature with an example, prerequisites, cost/permissions and a check. Feature activation uses existing feature_set approval rules; no promise of a new connector. For generated Skills, the owner reviews and approves the draft and grants; I cannot approve my own code, install arbitrary plugins or bypass a sandbox. HEARTBEAT.md is reserved, not a running scheduler. Physical motors/navigation and unimplemented integrations must not be invented.

## Updates, backups and troubleshooting
jarvis --help lists all commands; jarvis dashboard --help explains one command. jarvis update check checks for a release; jarvis update install asks before downloading, verifies the payload and backs up user data. No update link configured means release hosting is a maintainer blocker. Backups are local; secrets and face data are excluded, so never promise full credential recovery. Use jarvis backup --help before a backup/restore operation and have the user choose any restore.
Without internet or working AI: jarvis doctor, jarvis status, jarvis --help and jarvis logs --lines 30 work locally. Logs live under the private JARVES state directory's logs folder; ask only for relevant errors with secrets removed, not a full unreviewed log export. jarvis stop is orderly shutdown. Restart only when needed and requested. A successful mock/unit test is not a live account, mic, camera, playback or Pi check.
