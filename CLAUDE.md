# Claude Code — JARVIS

Follow `AGENTS.md` and the single active brief in `docs/NOW.md`.
Read extra documents only via `docs/CONTEXT_MAP.md`, on demand; `docs/DOC_MAP.md` is the index of all docs (per version, status, testing).
When the task is complete, add its handoff note as a NEW file `docs/handoff/<YYYY-MM-DD>-<topic>.md` (docs/handoff/README.md; never edit a shared handoff file, that made every two PRs conflict) and stop. Do not start the next task.
Every stage: research and use the newest best-in-class models/tools (see AGENTS.md "Best-in-class technology").
Work through commits: commit and push all results and open questions (in that handoff note), referencing the GitHub issue.
Every new feature, skill, command or integration ships with a guide: a `core/src/jarves/guides/data/<feature>.toml` entry (English and Hebrew, step by step, what it does, how to turn it on/off and fix it), a CLI parity entry, a features/capabilities row with an honest status, and Hebrew strings via `core/tools/catalog_add.py`. `test_guides` and `test_cli_parity` must pass. A feature without its guide is not done.
Every release from 4.1 and 5.0 on fixes all known bugs and issues before it ships: the bug tables in `docs/reviews/*BUG_TABLE*.md`, the open GitHub issues on igalgerman/jarves and the problems found by `jarvis selftest`/`speedtest` are triaged for that release. No open P0-P2 may remain; P3 items are fixed or listed with a reason and an owner decision. The release checklist records the bug-table state.
Use the time: never sit idle while CI or one task runs. Keep 5-8 sub-agents busy in parallel on independent work (features, bug sweeps, docs/Hebrew review, tests, CI/release tooling), each in its own git worktree and branch; when one finishes or waits on CI, start the next from the backlog (ROADMAP, bug tables, open issues, owner requests) at once. Check agent status regularly and restart anything that stopped or stalled. Agents rely on CI for full-suite evidence (targeted local tests only), never kill processes by command-line pattern, and use only the public igalgerman/jarves remote.
Run `python core/tools/prepush.py` before every push (docs/PREPUSH.md) and never push on a red local gate.
Pull request flow (how to merge, docs/GITHUB_FLOW.md): (1) run `python core/tools/prepush.py`, push, open the PR to `main`. (2) Turn on its auto-merge (`gh pr merge <n> --auto --merge`, or the GitHub MCP `enable_pr_auto_merge`): GitHub merges it the moment the required check `CI result (single required check)` is green, never before. High-risk PRs (the paths `core/tools/risk_class.py` lists: workflows, packaging, CLAUDE.md/AGENTS.md, security, updates, signing, release tooling) are checked by the coordinator first (read the diff, risk, tests, guide and docs rules, no secrets), then auto-merge is turned on. (3) Never merge `main` into a green PR just to bring it up to date: only to resolve a real conflict; the run on `main` after each merge is the integration check. (4) While the latest run on `main` is red, merge nothing else until it is fixed. No polling: after auto-merge is on, GitHub merges by itself; the agent only acts when a PR event says a check failed or a conflict appeared (a red PR stays open and never merges). Low-risk PRs (docs-only, tests-only, guides, Dependabot patch/minor) are labelled and merged by the `automerge` queue by themselves. No big integration batches: use an integration branch only for a few pull requests that truly depend on each other. Small pull requests, one risky CI change at a time and never together with a large merge.
Releases (docs/RELEASING.md): every green `main` publishes a beta by itself. A stable version is the owner's decision: the agent prepares `docs/reviews/RELEASE_CHECKLIST_<version>.md` and the test sheet (`python core/tools/manual_test_sheet.py --version <version>`), runs the release gate's dry run, and pushes the tag `v<version>` only after the owner's signed sheet is committed, 5 nightly runs in a row are green and the owner says go.
