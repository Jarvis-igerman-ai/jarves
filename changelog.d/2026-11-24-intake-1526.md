- Fixed: privacy mode now also scrubs goal plan text written before it was switched on (#1526). With privacy on at Core start, after it turns on, or after tool text was stored while it was off, the plan runner erases older step evidence in one memory.db transaction over the two plan tables. That transaction runs in a worker thread on its own short-lived connection with secure_delete on, so it never holds the plan store's lock; it reads all rows first and then writes them in two batched updates, and PLAN_SCRUBBED logs the rows changed and the scrub's duration in ms. A plan write made while that short write transaction is open waits for it (up to the shared connection's 5 s busy timeout). After the commit a PASSIVE checkpoint (it never waits) copies the scrubbed pages into the database file; older frames already in the write-ahead log, and pages freed before this change, are not forced out (no TRUNCATE checkpoint, no VACUUM). A failed scrub never stops plans; a failed or busy scrub (another writer for more than 0.5 s) is retried after a backoff (2 s doubling to 300 s) and logged once per outage. Stopping the runner waits for a running scrub. Step errors and plan notes keep only JARVES's own fixed reasons (one list of constants that every writer uses), cap notes or a whole result code; other text becomes "failed". A done plan's result keeps its `N. tool: status` lines, built by the same code as a new result; any other plan's result is blanked. Not scrubbed: a plan's title and each step's tool arguments and reason, which are the owner's plan and not tool output, so text typed there stays in memory.db.
