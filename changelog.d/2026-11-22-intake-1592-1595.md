- Fixed: projectmgr: while an agent run or check command runs, JARVES guards the git config files git reads: the repository's shared `.git/config`, the owner's global `~/.gitconfig` and XDG `git/config`, `config.worktree` files, every non-system file `git config --list --show-origin` reports for the worktree, every file an include names (also a missing one), and a worktree's `.git`/`commondir`/`gitdir` pointer files. A run that changes one is rejected and the file is restored (or removed again); every JARVES git call restores them first while a run is active, and a file that cannot be restored stays guarded after the run ends: every JARVES git call retries the restore and refuses to run until it succeeds; the restore is tried even when keeping a backup failed, and a restored file keeps its permission bits. While a file is unrestored, a new agent run or check command is refused before it starts. A rejected worktree `.git` pointer is kept in the worktree's gitdir, not inside the worktree (#1592). Any change during a run is reverted, the owner's own included: the replaced content is kept in a `<name>.jarves-rejected-*` folder next to the file, named in the rejection and logged as PROJECT_GIT_CONFIG_RESTORED; a restore that keeps failing on the same content keeps one backup and logs once. The trusted copy is taken under the guard lock after restoring, so a run that ends while another starts can never make its planted entry trusted. JARVES's own git calls no longer write config (`branch.autoSetupMerge=false`, `worktree.useRelativePaths=false`). Not guarded: the system config, an owner-set GIT_CONFIG_GLOBAL, an include inside an included file that does not apply to the guarded worktree, and a conditional include that applies only in another folder. The GitHub branch push (`forge.push_branch`, no caller yet) now goes to a pinned `https://github.com/<owner>/<repo>.git` from a private temporary repository with no repository, global or system config (GIT_CONFIG_GLOBAL empty, GIT_CONFIG_NOSYSTEM=1), using only the owner's gh login as credential helper and `http.sslVerify=true`; on Windows it pins `http.sslBackend=schannel`, because GIT_CONFIG_NOSYSTEM also drops Git for Windows' system TLS backend (#1595).
