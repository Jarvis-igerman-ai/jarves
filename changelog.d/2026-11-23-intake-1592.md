- Fixed: on Linux a project's check command now runs in its own user, mount, PID and network namespaces (kernel 5.12+). This also applies when an agent runs the check: it does so through a `jarves-check` script, named by its absolute path, that passes on only the allow-listed environment. Inside, the whole file system is read-only except the run's worktree (not its `.git` pointer). `/tmp`, `/var/tmp`, `/dev/shm`, `/run` and `~/.cache` are empty private folders, and every other bound unix socket path is covered (more than 4096 such sockets fails the run instead of leaving some reachable). The check has no network, and it cannot see, trace or signal any process outside. Every process it starts ends with it. So task code can neither change nor rename the repository's shared git files or their folders, nor plant code in the owner's home or reach the owner's daemons. If a run cannot be confined, or the confinement probe fails for an unknown reason (for example a timeout), the run fails and the next run probes again. Only where the kernel reports that user namespaces or the needed mount calls are unavailable, and on Windows and macOS (#1665), checks run as before and JARVES logs that once. The owner's release command is not confined; that scope is the owner's decision. (#1592, JAR-746)
