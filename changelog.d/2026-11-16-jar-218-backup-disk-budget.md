- Fixed: beta installs no longer fill the disk with backups (#1016, JAR-218). An install takes one verified backup (a checkpoint, not a manual backup) and the updater reuses it as the rollback backup instead of writing a second one, but only while it verifies, is in the backup folder and no data file changed during the download (otherwise it takes a fresh one, so a rollback never restores stale data); the next Core start reuses it only when no data changed since. The running Core usually writes during the download, so an install usually still takes two or three checkpoints, all kept within `checkpoints` and `max_gb`. Downloaded installers (`updates/*.exe`) are no longer copied into every backup. New size limit for all backups together (`max_gb`, default 4 GB): the oldest automatic backups and checkpoints go first; manual backups, the newest backup, the rollback backup and a backup being restored are never removed by it. Before writing, a free-space check prunes first and stops with `BACKUP_NO_SPACE` instead of filling the drive. New defaults: keep 5 manual backups (was 10) and 3 checkpoints (was 5); the first prune after updating removes the extra older ones (raise them with `jarvis backup settings --manual 10 --checkpoints 5`). `jarvis backup list` shows the total size; doctor warns when backups are over the limit and points at manual backups (`jarvis backup settings --manual N`), which the limit never deletes.
