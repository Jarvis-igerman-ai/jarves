- Fixed: project manager: an agent or check that changes the shared git files JARVES git reads (the repository's `config`, `config.worktree` and `info/attributes`, your `~/.gitconfig` and `~/.config/git/config`/`attributes`, and any file these include through `include.path`/`includeIf.*.path`) fails, and the files are put back (the newest 5 rejected copies are kept; the file gets back its original mode). Your user-level files have one baseline shared by every project, so a filter planted there by an agent in one project never runs in another. After the last run, only `remote.*.url/pushurl/fetch` (not `ext::`/`fd::` or other `<helper>::` URLs), `branch.*.remote/merge/rebase` and `user.*` edits are accepted, so `git remote add` keeps working; any other change stops JARVES git in that repository (in every project for your user-level files) until restart, and the message names the added `key=value` entries. JARVES worktrees use the git folders read when they were made; after a restart, an integration, task or release worktree that does not point into its own repository is refused on first use (#1533). Not covered: the admin-owned system config and a custom `core.attributesFile` path.
