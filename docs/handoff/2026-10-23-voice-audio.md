# Handoff 2026-10-23: voice and audio on the owner's PC (issue #17)

Branch `fix/voice-audio` (no PR opened). Evidence came from the owner's Windows PC (Realtek mic array, laptop speakers, no headset). Nothing here was heard or played: there is no microphone or speaker in the build environment, so everything is proven with synthetic frames, fake clocks and fake connections (`core/tests/test_voice_audio17.py`).

## Root cause per item

1. **False wakes (35 wake_false, 39 "nobody spoke").** The owner's `voice.wake_threshold` is 0.15 (the `jarvis wake test` recommender floored at 0.15). In the two-stage pipeline that value is not used (accept = max(threshold, 0.5)), but in the single-stage fallback (speech check unavailable) 0.15 fires on room noise. In two-stage mode a score above accept woke with no check at all. Also nothing learned from the false wakes: selfcheck only suggested +0.05.
   Fix: `voice/wake_guard.py` keeps a local log of wake outcomes (time and good/false, no audio) in `wake/outcomes.json`. 3+ false wakes in 24 h raise the accept threshold by 0.08 per level (max level 4), shorten the first-word wait (12 s to 6 s), and from level 2 require the local speech check even for strong scores (`ConfirmingDetector.always_confirm`). Single-stage threshold floor 0.25. After a conversation ends the wake word is deaf for 1.5 s (JARVES's own speech tail). `jarvis wake test` prints the measured rate and the advice; the recommender floor is 0.25; `--apply` clears the log. Logs `WAKE_AUTO_TUNED`.
2. **Echo and "kept answering while the user talked" (39 chunks dropped).** Half-duplex silences the mic towards the model while JARVES speaks, so a user talking over it was never heard and the model's reply was dropped chunk by chunk instead of stopped. Fix: `voice/echo_gate.py` compares the local mic level with the learned echo level; 0.3 s well above it (3x echo, min 0.05, cold start 0.12) is the user: speech is flushed (`interrupt()`), the mic opens for 1.5 s and the last 3 chunks are sent as pre-roll. Echo alone never sends audio to the model. Log `LIVE_ECHO_BARGE_IN`. No ducking was added.
3. **Dead air (9-13 s silence, replies up to 5.9 s late, stalled 21 s).** The spoken progress note depends on the server accepting it. When it was rejected, `progress_after_s` was set to 0 for the whole session, so the next slow lookup was silent (links to item 4). Fix: a local two-note soft cue (`_dead_air_cue`, no network) 3 s after the user stops with no JARVES sound, every 5 s, max 4 per turn; not during user speech, approvals, or quiet hours (`calm.quiet_hours_now`) and only while `voice.chime` is on. New `LIVE_LATENCY` log per reply with stage timings (to_delegation, delegation_to_backend, backend, backend_to_audio, model_direct), `slowest`, warning when 5 s or more. The stall deadline (`voice.backend_deadline_s`, default 25) and retry path already existed and were left unchanged (tests and docs pin 25).
4. **LIVE_EXTRA_REJECTED (x19).** Not a format bug that I can prove. The V4 campaign already saw `context_injection_incomplete` (a note arriving while the server is still applying earlier context). The real provider message is in the `provider_error` field of the owner's log, which I could not read. Fix: transient rejections no longer switch features off on the first hit (off after 3, or at once for a non-transient code); only the first rejection per kind is a WARNING (rest DEBUG, counted in `extras_rejected`); announcements rejected as incomplete are resent unchanged once instead of halved. The local cue covers the user either way.
5. **5 unclean shutdowns.** Not reproducible. Provable gaps fixed: no SIGTERM/SIGBREAK handler (Windows console close, `taskkill`, service stop killed the process with no `CORE_STOPPED`); now they request the same stop as tray Quit. `Core.stop()` waited unbounded for cancelled tasks (the wake loop closes a PortAudio stream); now bounded at 6 s with `CORE_STOP_TASKS_STUCK` naming the tasks. A hard kill, power cut or Windows shutdown cannot be handled in code.
