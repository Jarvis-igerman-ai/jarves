# V6 #220: Skills Platform 2.0 wiring (manifest v2 trust, update, rollback), 25 Oct 2026

Branch `v6/skills-wire-220`, label `no-automerge` (HIGH RISK: Skills trust and approvals; independent review ordered).

## Done
- `core/src/jarves/skills/platform2.py` (new): `check()` (trust state + manifest facts; tampered or invalid manifest 2
  = errors = refuse), `approved_sha()`, `plan_update()` (uses `manifest2.plan_update`; lists added/removed permissions,
  always `needs_approval`, refuses tampered/invalid), `owner_key()` (reads `<home>/skills/owner.key` only, never
  creates one), CLI `jarvis skills list | update NAME [--approve SHA256] | rollback NAME [--yes]`.
- `skills/generated.py`: a `v2` switch callable (Core: `features.active("skills_manifest2")`; dashboard: the ctx
  features, off when unknown; CLI: `_cli_features`). With the switch ON: propose/approve add `manifest2` facts and
  fail closed on tampered/invalid; sync does not register and run() refuses (`SKILL_TAMPERED`) an installed version
  whose files differ from the approved sha256 or whose signature is tampered; rollback refuses a stored copy that
  differs from its approved sha256 (grants are still cleared); `view()` and `draft()` show trust and the update plan;
  the summary text shows version and trust. With the switch OFF nothing changes (parametrized tests prove it).
- Bug fixed on the way: an approve after a rollback reused the kept version folder (`mkdir(exist_ok=False)` crashed);
  new versions now take max(existing)+1.
- A manifest-2 Skill may request `storage` / `network:<host>` under `permissions` (only while the switch is on);
  these are still only requests that the owner grants.
- Guide `guides/data/skills_manifest2.toml` (EN+HE, update/rollback steps, problems, `[parity.features]` -> `skills`),
  old shared parity entry removed, feature row text and evidence updated (still `implemented_unverified`), Hebrew via
  `hebrew.TEXT` + `catalog_add.py` part, `docs/SKILL_CREATION.md` section.
- Tests: `core/tests/test_v6_skills_platform2.py` (unsigned / owner_signed / tampered x3 / invalid, added-permission
  plan, tampered update refused, rollback clears grants, sha256 mismatch refuses rollback and loading, v1 flow
  unchanged on/off, model cannot update/rollback/approve, logs hold no Skill source text, CLI, dashboard default off).

## Not done, and why
- Built-in example v2 Skills `timers` and `lists`: SKIPPED. Generated Skills run in the key-less sandbox and can only
  use `ctx.storage/http_get/now/log`; they cannot call the real timer and list stores (memory.db, rung by the Core),
  and the ids `timers` / `lists` are taken by the built-in Skills, which `validate` refuses. Doing it needs either a
  new sandbox capability to call Core tools (a new dangerous capability) or attaching manifests to built-in Skills
  (a registry change). Both are out of this PR's safe scope.
- No dashboard UI change: the New Skills page shows trust through the existing summary text; `update_plan` is in the
  draft JSON for a later UI.
