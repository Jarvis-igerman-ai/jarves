## Where the minutes go (one 21-min PR run, id 41748018086)

- Quick gate and classify finish about 1 min after start.
- Heavy jobs start 4 to 9 min later (first at +4.8, Windows shards at +9 min): runner queue wait, not work.
- Core shards then take about 10 min each (Linux 10.4/11.1/10.5, Windows 9.0/9.5/9.3/7.9), balanced within about 1 min.
- Installer upgrade and rollback (9.6 min) runs parallel to the shards, so the shards set the wall time.

Reading: the plan items (S1 to S5) are all on main, so the remaining gap is runner contention (about 25 jobs per full
run, many runs in parallel, merge-group reruns cancelling each other) plus about 10 min of pure shard work. Sharding is
already balanced, so more shards would add runners without cutting the queue wait.

## Decision

No workflow change in this task: no change is both safe and supported by this data (`jarves-checks.yml` is Tier R, and
the main cost is queue wait that depends on how many runs run at once). Candidates for a later, separate Tier R PR with
its own review:

1. Fewer concurrent full matrices: skip the full PR matrix for PRs that are re-tested in the merge group. Needs an owner
   decision on the required PR proof.
2. Measure queue wait directly (job `created_at` to `started_at`) in `ci_health.py` so the daily comment separates wait from work.
3. Reduce Core shard work (about 10 min each), for example by profiling the slowest test files in the `shard-timings` summary.

Verdict: the #160 plan is delivered; the speed target is NOT met (24.6 min PR median against under 8). Keep #160 open as the tracker.
