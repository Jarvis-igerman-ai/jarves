# JAR-641 (#1390) blocked: shared git config cannot be neutralised race-free

Date: 21 Nov 2026. Ticket JAR-641, review-restart after PR #1502 (closed after 2 fix rounds and a Doctor pass).

## What the review asks
Fix all findings R1-R5 of the PR #1502 review, together with the base fix of #1390. The base fix covers filters,
merge drivers, diff drivers, fsmonitor, ssh/editor/credential/gpg programs and config hooks. The budget is about
200 changed lines.

## Why this is blocked
1. **R1 (time-of-check/time-of-use) cannot be fixed by any `-c` override design.** Git always reads the
   repository's own `.git/config` and the files it includes. No environment variable or option turns that read
   off. `-c` can only replace a key whose exact name JARVES already knows. Filter, merge-driver, diff-driver,
   `hook.<x>` and `http.<url>` keys use names an agent chooses, so JARVES has to read the config first to learn
   them. An agent that writes a new name between that read and the real git call wins the race. PRs #1468, #1486
   and #1502 all used this read-then-override design.
2. **Switching off the trigger has the same race.** A filter runs only when an attribute names it. But
   `$GIT_COMMON_DIR/info/attributes` sits in the shared `.git` folder, so agents can write it, and git reads it
   even with `GIT_ATTR_SOURCE` set to the empty tree and `core.attributesFile=/dev/null`. Checked with git 2.43.0:
   ```
   git init -q r && cd r && git config filter.evil.clean 'echo ran >> ../ran.txt; cat'
   echo '* filter=evil' > .git/info/attributes && echo x > a
   GIT_ATTR_SOURCE=4b825dc642cb6eb9a060e54bf8d69288fbee4904 git -c core.attributesFile=/dev/null add a
   cat ../ran.txt   # -> ran
   ```
3. **Size.** PR #1502 already changed about 400 lines and did not cover R2 (`http.proxy`, `http.<url>.sslVerify`,
   `extraHeader` and similar keys), R3 (`remote update`/`add -f`/`show` reaching the transport) or R4 (`GIT_SSH`
   precedence). R2 has no closed key list either: `http.<url>.*` is URL-specific and beats any plain `-c http.*`
   value.

## Decision needed (owner)
- **A. Separate clones for agents (recommended).** Each task agent works in its own clone with its own `.git`,
  not in a `git worktree` of the owner's repository. JARVES fetches the agent's commits into its own integration
  repository, using only https/ssh/file transports with git's own pack programs. Agents then never write the
  config that JARVES's git reads. This closes #1390, R1 and R2 and the #1381 hook class at the source. It is an
  engine change of more than 200 lines and needs its own ticket and design review.
- **B. Accept the race as a documented residual risk.** Resubmit the #1502 design trimmed to the issue's own list
  (fsmonitor, filters, merge drivers). Record R1/R2 as accepted follow-ups. The reviewer has to agree that R1 is
  not blocking.
- **C. Stop agents from writing the shared `.git`** (sandbox or permission rule for agent processes). This depends
  on each agent CLI's sandbox, so it is UNVERIFIED on Windows.

Nothing in the product changed in this PR.
