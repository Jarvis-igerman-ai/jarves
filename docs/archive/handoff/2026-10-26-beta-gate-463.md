# Generic beta-features gate (#463) - 26 Oct 2026

- Registry: every feature has `stage` ("stable" | "beta"); `features.stage_of(id)`: explicit `register(stage=...)`, else derived from the capabilities table (Windows `verified_on_device` -> stable, anything else or undeclared -> beta). A new feature is beta and OFF until its evidence is recorded.
- One global opt-in `beta_features` (features.json, default OFF). `Features.enabled()` is False for a beta feature while it is off (saved choice kept); `Features.set(beta, True)` raises `BetaLocked` ("beta feature: turn on beta features first"). Every path ends in `Features.set`: CLI, dashboard POST, phone enable, voice tool, guides step, Settings skill, wizard bundle, autonomy, camera face button, google_setup, self_manage.
- Migration: an install with `features.json` or `setup_done` and no recorded choice is switched ON once (nothing breaks, features are labelled beta). A fresh install records OFF (wizard step "Beta features"). `JARVES_BETA_FEATURES=1` forces it on (tests/CI).
- Surfaces: `jarvis features beta on|off|status`, `jarvis features` list shows the stage, Features page switch + stable/beta pill (`POST /api/beta-features`), wizard step + hidden beta cards, guide `beta_features`.
- Stable by explicit decision (platform plumbing, not feature claims): `dashboard`, `text_chat`, `update_check`, `beta_channel`. The update channel stays separate.
- Tests: `core/tests/test_beta_gate.py` (all registered features x all enable paths); the conftest turns the opt-in ON for the older tests.
- Owner decision to confirm: which features count as stable (only 4 are `verified_on_device` today, so most of the catalogue is beta).
