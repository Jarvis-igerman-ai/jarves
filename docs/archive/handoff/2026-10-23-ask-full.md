# `jarvis ask --full` / `jarvis tell`: one message with full access (issue #17)

**Problem (owner, real PC):** `jarvis ask` builds its own small tool set (Clock, Memory, LocalContacts, Music) and answers
"I can't check your WhatsApp messages". `jarvis chat` has every Skill but is interactive only, so the owner could not script
or quickly test full JARVES.

**Design:** `jarvis ask --full "..."` (and the second name `jarvis tell`) sends ONE `chat.turn` to the RUNNING Core over the same
local link and protocol as `jarvis chat` (`chat_cli.LinkTransport` + `ChatSession.wait_for`). `AskSession` subclasses
`ChatSession`; no registry or brain is built in the CLI. `ensure_core` starts the Core when needed (`--wait`).
- Silent by default (`silent: true`, no voice); `--speak` sends `voice: true` only if the Core can speak and it is not quiet hours.
- Streams the answer, prints tool lines as `chat --verbose` does. Exit 0 = normal answer; 1 = CORE_INTERNAL, Core not reachable /
  connection closed, TIMEOUT (`--timeout`, default 300 s, sends `chat.cancel`), CANCELLED, any not-ok answer; 2 = no text.
- Text: words given, else stdin (`echo "..." | jarvis ask --full`).
- Approvals: interactive terminal keeps the chat y/N (hidden code) prompt; a non-interactive stdin uses `DenyLines`, which prints
  "approval denied" and answers "no" (a piped `y` is never an approval).
- `--json`: stdout is one object `{ok, text, tools:[{name,ok,code}], code}`; human lines go to stderr.
- Plain `jarvis ask` is unchanged (same tools, offline-simple); its help string says "limited tool set: use --full for every
  Skill" and a failed answer or an "I can't / no access" answer prints a hint to stderr naming `--full`.

**Files:** `core/src/jarves/chat_cli.py` (DenyLines, AskSession, read_ask_text, run_ask), `core/src/jarves/cli.py`
(cmd_ask_full, parser: `ask --full/--json/--speak/--timeout/--wait`, `tell`), `core/src/jarves/cli_parity.py` (ALSO),
`core/src/jarves/guides/data/ask_full.toml` (EN+HE guide), `core/src/jarves/setup_guide.md` (one sentence),
`core/tests/test_ask_full.py`. No new feature switch: it uses the existing `text_chat` feature and the same Core path.
No dashboard strings added, so `catalog_add.py` had nothing to add (CLI Hebrew is inline via `clilang`).

**Based on** `origin/fix/chat-context-wrapper-on-delta` (PR #100, not yet in main): without it every chat turn fails with
CORE_INTERNAL. Rebase on main once #100 merges.

**Not verified:** a real Core on the owner's Windows PC (WhatsApp/calendar skills, real approval popup next to the terminal,
`--speak` through a real speaker, Ctrl+C on Windows). Tests use a real in-process Core with a fake model.

**Decisions needed:** none.
