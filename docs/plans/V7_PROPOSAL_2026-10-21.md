## 4. V7 core — vision stage 4 (Android Daily Companion)

**User outcomes:** phone app to talk to the same JARVES in Hebrew; resume PC/car conversations; see tasks, memory-justified suggestions, approvals, upcoming reminders, development status; voice first with an uncluttered native interaction, not only a mobile webpage. Phone notifications/actions respect explicit device permissions. Show PC unreachable/offline truthfully. Start with the PC-hosted authoritative Core proven in V5, select limited optional on-device fallbacks only after measurement.

**Mandatory Android feasibility research:**
1. Kotlin/Compose native shell versus hybrid wrapper; choose smallest maintainable implementation and reuse the V5 phone client where reasonable.
2. Voice and assistant role: evaluate Android `VoiceInteractionService`, role/user selection, push-to-talk, background microphone and foreground service limits; distinguish API existence from eligibility on target OEM/version. Android 14/17 restrictions matter. [voice API](https://developer.android.com/reference/android/service/voice/VoiceInteractionService) · [background FGS restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start) · [Android 17 audio hardening](https://developer.android.com/about/versions/17/changes/bg-audio).
3. Consentful device Skills: share selected text/files/URLs to JARVES, relevant notification actions and local reminders, calendar/maps/music deep links, push notifications and an accessible widget/shortcut. Restrict each by Android APIs, app policy and per-skill prompts; never claim global accessibility/device control.
4. Seamless phone↔PC↔car handoff (V5/V6 foundations): no duplicate notification/task or stale audio route.
5. Test on actual Samsung/Android and later additional Android OEMs: service lifecycle, battery, locked screen, mic permissions, incoming calls, Bluetooth, reconnect, Hebrew right-to-left, accessibility, privacy indicators and crash/restart.

**Non-goals:** uncontrolled always-on listening, replacing system Gemini/assistant by force, screen-wide UI automation by default, a second isolated memory brain, privileged Android APIs without policy-compliant access. Stage 5 docked phone as robot and stage 6 physical build remain subsequent product milestones.

## 5. Browser Studio — supervised, observable browser workflows

**Desired user journey:**
1. JARVES receives a bounded user task (research, open a webpage, sign up, check order, fill permitted forms) and asks which website/account scope is authorized.
2. It opens a **dedicated session**. Dashboard/phone shows **Watch live** (streamed view, distinct from a saved video), current URL, progress, planned next action, privacy/mic indicators and a clear **Stop**.
3. It may save a **screen recording/video** or replay only on explicit opt-in. Reports the real format: MP4 if actually generated, rrweb/trace if not; do not mislabel structured event logs as a video.
4. At login/2FA/MFA/payment/complex UI: **PAUSE agent** → user taps **Take control** and operates *the same session* → **Return to JARVES**. Agent cannot issue clicks/keyboard during takeover, and must re-read the page after return. Secrets are never pasted back into a model prompt by design.
5. For consequential actions (send, purchase, submit, publish, delete): preview intention and obtain specific, logged confirmation. Browser's mere ability to click is **not** permission.
6. Finish: verify result using page evidence, provide link/result, show costs/time and recording when enabled, close/revoke disposable session.

**Proof matrix / acceptance:**
- Local Playwright headed browser + scoped Chrome profile vs Browser Use managed session vs Cloudflare/Aether supervised browser; compare Windows/Android viewer, latency, cost, login persistence, recording, accessibility tree, security, maintenance and vendor lock-in.
- Demonstrate watch/takeover/release with a non-sensitive test website and then separate user-approved login sandbox; verify true single-session state continuity.
- Require authenticated live-view URL, session expiry/revocation, no public VNC/exposed local ports, allowlisted navigation / SSRF guards and download isolation.
- Recording disabled by default; retention policy, deletion, capture pause during sensitive steps, encryption and external sharing rules. Tests for phishing/prompt injection in website text, credential leaks, stale control ownership, auto-submit bypass and user cancellation.
- Separate *user-requested browser work* from the current assistant's basic web search; use the latter unless clicks are truly required. Prevent browser tools from silently using logged-in personal accounts.

**Recommendation:** read-only local browser + live view pilot first. Add human handoff next. Add explicit video/recording only if quality, privacy, complexity and hosting are acceptable; *do not make full video production a prerequisite to basic browser competence.*

## 6. Model Lab — assistant **and software-development team**

**Requested scope is deliberately two-sided:**
- **JARVES task execution:** Hebrew Q&A, retrieval, planning, tools, browser planning, skill calls, factual grounding, memory-enabled responses, optional local/offline routes.
- **Development agents:** Claude Code, Codex and new OpenCode; model eligibility depends on each harness/provider/account's published support. OpenRouter connectivity through OpenCode does **not** automatically mean an unrelated Claude/Codex plan or session permits arbitrary OpenRouter models.

**Proposed shared policy layer:** one `ModelRegistry`/provider capability view, explicit user-selectable per-task or per-agent model/profile, tracked run metadata and separate budgets. Do not forcibly route every harness through an undocumented proxy. Modes: `balanced`, `best-quality`, `cheap`, `free-only`, `local-only` with **explicit** non-silent policy exceptions.

**Evaluation benchmark (repeatable datasets):**
- Hebrew normal/colloquial speech and errors; multilingual instructions; intent/follow-up.
- Tool correctness: schema, argument fidelity, correct confirmation and no fictitious side effects.
- Coding: small JARVES patch, Catch2/Python tests, bug diagnosis, regression, maintainable PR review; evaluate actual test pass and reviewer judgments, not model self-score alone.
- Latency: time-to-first-result, full completion, fallback rate, retries, rate-limit failures.
- Cost: token usage, provider price/fees, *actual paid or free status*, retry overhead; compare **cost per accepted task**, not just cost per million tokens.
- Stability/consistency: named fixed model versus `openrouter/free` randomized provider/model; log resolved model and availability.
- Secret/privacy posture: code/data handling, provider region and retention, no free-provider private code transmission without explicit policy.

**No-charge evaluation first:** use fake provider and prerecorded cases for plumbing; live trials separately authorized. Free tier **may still have request caps** or changing models. Disable paid fallback automatically when `free-only` is selected; retain the upstream hard spending caps/account balances. Publish a human-readable Dashboard comparison table and a small JSON/CSV result archive without secrets.

**Agent assignment examples:** cheap model for docs/lint/test summaries, stronger for architecture and complex fixes, independent reviewer model for consequential diff. Do not hardcode vendor preferences; measured quality and costs decide. Prevent concurrent writers clobbering branches: one task owner/isolated worktree; reviewer read-only.

## 7. Development Manager, OpenCode, GitHub and candidate Buzz

**Integration order and boundaries:**
1. Inventory existing Development Manager/Orchestrator status endpoints and GitHub tracking in V4/V5. Avoid parallel custom implementations.
2. **OpenCode adapter**: API health, discover sessions/status/selected model, events, read-only recent actions and linked git worktree. Confirm actual mutating/interruptible APIs before steering; don't assume a CLI command can attach to a different session transparently.
3. **GitHub**: read repos/branches/Issues/PRs/CI with scoped token or existing authorized GitHub connector. Associate running agent → branch → PR → failed check → required user action. Optional write action only after granular permission and confirmation. No auto-merge/deploy.
4. **Buzz/ACP research**: if the intended "buz" is Block's Buzz, prototype a narrow workroom/agent-status bridge or borrow shared-room events, approval handoff and durable activity feed; document hosting/storage/admin burden. If user meant a different “Buz”, replace this candidate without treating Block Buzz as already approved.

**Owner-visible features:**
- “What is Claude/Codex/OpenCode doing?” one status dashboard with real freshness and stale-session flags.
- “Review latest failed CI” gives verified GitHub run, commits and concise repair suggestion.
- “Send a follow-up to OpenCode” preview exact task, target repo/branch/session, cost/permission and submit only on approval.
- Human+AI activity room optionally via Buzz, rather than requiring the household JARVES to become an enterprise communication product.

## 8. Additional small high-value ideas (select, do not promise all)

1. **MCP registry and compatibility checks:** connect approved external tools/Skills via a single audited capability registry; avoid uncontrolled plugin downloads.
2. **Action receipts:** every important operation links to real target (PR, calendar event, webpage, email) and a success/failure reason; never report success solely from a model response.
3. **Workflow recipes:** “morning agent/CI brief”, “scan open PRs”, “research price and ask before purchase”, “prepare event and approval”, with bounded budgets and stop/pause.
4. **Local model fallback research:** optional Ollama/llama.cpp tests when PC offline; measure real speed and Hebrew correctness before any default routing or Pi promise.
5. **Skill trust profiles:** `read-only`, `draft-only`, `confirm-before-write`; permissions attach to identity/device/account/task, not to the model's asserted intent.
6. **Browser replay + quality review:** replay deterministic steps with evidence and incident triage; structured trace plus optional video. Record exact user approvals in a separate minimal audit trail.
7. **Agent benchmark dashboards:** 7/30-day completion/cost/error trends, no leaderboard claiming objective superiority from tiny samples.
8. **Voice performance budgets:** use already selected V6 audio engine; measure only gaps relevant to native Android, avoid wholesale switch to LiveKit/Pipecat based on hype.

## 10. Open uncertainties and explicit contra

- **“buz” identity:** not conclusively identified. Working candidate is [Buzz by Block](https://github.com/block/buzz), but could refer to something else. Keep optional, do not integrate before confirmation.
- **Browser recording vs live view:** these are distinct features. MP4 in some products; Cloudflare trace is structured session data. Video may expose passwords/PII; consent and masking are design gates.
- **Android voice default-role/hotword:** official service class exists, but implementation, OEM, user role and background policies differ. No promise of always-on private assistant or replacement for Gemini based on Android documentation alone.
- **Free models:** availability, rate limits, prompt handling, speed and tool quality fluctuate. They can save cost for routine work yet fail costly coding tasks. Compare *total accepted result cost* and preserve non-free fallback policy.
- **Framework import temptation:** OpenClaw/Buzz capabilities look broad, but cost of maintaining extra runtimes may exceed the value. Prefer small adapters unless a real benchmark disproves this.
- **Remote browser access:** ephemeral live URLs and takeover must be authenticated, scoped and revocable; never publish local browser/VNC ports or reuse an unrestricted owner Chrome profile.
- **Code privacy:** arbitrary new routing of repository contents to third-party free models requires owner-approved disclosure policy, per-project trust setting and explicit provider choice.
- **Production confidence:** all findings in this file are **documentation-based candidate assessments**, not proof these integrations already work inside JARVES.
