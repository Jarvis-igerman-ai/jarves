# CI speed plan, 26 Oct 2026 (owner order: increase delivery speed permanently)

Scope: `jarves-checks` wall clock per PR run and per merge-queue group, without weakening safety (required checks
`CI result (single required check)` and `Auto-label policy` stay; no skipped real coverage; no paid runners). Builds on
issue #160 (E3) and `docs/CI_PERFORMANCE.md`.

## Measured (runs 25-26 Oct, 40 PR runs and 30 merge_group runs with job timings; 400 run records)

| Event | Median wall (create -> `CI result`) | p90 | Runs: success / failed / cancelled |
|---|---|---|---|
| pull_request | 15.2 min | 23.8 | 108 / 30 / 53 (cancelled = superseded by a push, 288 wall-min in total) |
| merge_group | 15.9 min | 19.1 | 101 / 10 / 11 |
| push main (proof reused) | about 2 min | | 84 / 0 / 1 |

The 40-60 min a PR waits in the queue is NOT the run time (a group is 16 min median, 19 p90): it is groups waiting for each
other, because one group already uses about 21 jobs of the 20 free-plan runners.

| Job | Run min (median / max) | Start offset after run created (median) | Notes |
|---|---|---|---|
| Installer upgrade and rollback | 9.4 / 11 | 6-7 | critical path of every merge group (installer 4.0 -> upgrade 9.4 = 15.2 of the 15.9) |
| Real-browser tests (Linux) | 7.6 / 23.3 | 1 | 14 of about 80 PR job runs failed once and re-ran the WHOLE browser suite: tail 15-23 min |
| Python Core Linux shards 1-3 | 6.8 / 9.2 | 1-2 | skew small |
| Python Core Windows shards 1-4 | 6.2 / 12.9 | 1-3 | p90 8.2; median skew between the 4 shards 1.9 min; shard 4/4 failed 6 times in PRs (flake) |
| Performance gate | 5.1 / 5.6 | 1 | not on the critical path |
| Windows installer build | 4.2 / 4.6 | 1 | |
| Installer smoke (4 scenarios) | 1.9 / 5.6 | 6 | after the build |
| E2E, bridge, cad, blender, godot, validate, classify | 0.2-1.5 | | negligible |

Critical path: PR run = slowest of 7 Core shards + 2 browser jobs (about 8-9 min) plus the 1-3 min start offset plus
retry tails; merge group = installer build -> upgrade/rollback scenario. Flake/retry rate: PR job failures that need a
re-run: Real-browser 14 (Windows 7, Linux 7), Windows Core shard 4/4 6, Linux shard 2/3 4; merge groups: 4 Windows shard
failures in 30 groups. 16 percent of PR runs and 8 percent of groups end red; about 27 percent of PR runs are cancelled by
newer pushes (expected, cheap).

## Already in place (nothing to do)

(1) concurrency + cancel-in-progress for PR pushes only (`concurrency:` block; merge_group and main never cancelled; a
`supersede` job cancels older groups of the same PR). (2) path filters: docs/guides-only runs skip heavy jobs
(`ci_plan.py classify`), installer chain only on PRs that touch packaging (PR_INSTALLER). (3) uv cache, Playwright cache,
tool cache (Godot/Inno), duration caches. (4) shards planned from measured durations, 4 Windows and 3 Linux shards. Main
reuses the PR/merge-group proof by tree hash. Merge queue (read only): build concurrency 3, merge up to 4, min 1, wait 2 min,
ALLGREEN, check timeout 60 min.

A 50 percent cut of the median is not reachable by trimming: the installer chain alone is 13 min and is real coverage. The
realistic gain is p90 (-8 min, R1), fewer red re-builds (R2) and 30 percent on the group critical path (R3/R4, each its own
reviewed PR).
